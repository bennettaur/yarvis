Yarvis

Running my week with an assistant
that can start the work

How I plan, start, steer and wrap up a week of work across many parallel coding agents, and how to get the most out of each part of Yarvis.

Set the frame: this isn't a tour of every button. It's how I actually use Yarvis across a week, and which features make each step work. Setup instructions are in docs/getting-started.md, or run /yarvis-setup in Claude Code.
The problem

My work is spread across a dozen places, and none of them remember anything

A normal day with coding agents looks like this:

  • Four or five Claude Code sessions, each in its own checkout
  • PRs to write, PRs to review, CI to babysit
  • Tickets in JIRA, issues in GitHub, tasks in my head
  • Meetings that I will miss if nothing yells at me
  • Every Monday: "what was I doing last week?"
  • Every afternoon: "which agent is waiting on me?"
  • Every Friday: "what did I actually ship?"
  • Every review: re-learning code I read last month

The agents do the work well. What was missing was something that keeps track of the work around them.

The pain isn't the coding. It's the context switching and the lost thread. Most of the questions on the right are things I used to answer by scrolling through terminals, GitHub notifications and my own notes.
What Yarvis is

One desktop app, three layers

A macOS app (Tauri, React, a Bun sidecar, Postgres with pgvector). Your data stays in a local Postgres. LLM and integration calls go out to those services.

The assistant

  • Knows my projects and their priorities
  • Keeps my tasks and its own todos
  • Remembers facts, decisions, feedback
  • Logs what I actually did
  • Starts work and steers running agents

Workspaces

  • A folder per piece of work
  • A git worktree per repo, one branch
  • A Claude Code session at the root
  • Diffs, self-review, PR checks, stacks
  • A bell when a session needs me

The day's tools

  • PR review with guided tours
  • Terminals, Omni Chat, Omni view
  • Calendar and full-screen alarms
  • Voice, clipboard palette, Telegram
  • MCP in both directions
The assistant is the center. Workspaces are where agents do the work. The tools around the edge are there so I don't leave the app during the day. They also feed the activity log, which is how the assistant knows what I did.
The weekly loop

Plan, start, steer, wrap up. Then do it again.

Monday
Set priorities

Tell the assistant what the week is for, which tickets matter, and what's due when.

Any time
Start work

"Start work on PROJ-412." A workspace, a worktree and an agent on the ticket.

All week
Ask and steer

"Where did we leave off?" "What's next?" "Merge main into my open PRs."

Friday
Wrap up

"What did I get done this week?" A write-up with every PR named.

Everything along the way lands in memory and the activity log, so next Monday starts from where this week ended.

  • A project with a focus for the week
  • Each ticket tracked with the priority I said
  • Tasks for my goals, daily or weekly
  • A todo for what the assistant promised

All of it is visible and editable: projects under Memory → Projects, tasks on the Tasks tab, and the assistant's promises under Memory → Agent todos.

The key habit: say priorities out loud. "PROJ-412 is urgent" gets stored and used for the rest of the week. "Let's look at PROJ-412" doesn't. Tasks are my plan. Agent todos are the assistant's promises, kept separately so they survive the conversation without cluttering my list. For a big project, I ask it to reconcile against JIRA, which goes to the project-manager specialist.
Start work

One sentence to a running agent on the ticket

Chat
Start work on PROJ-412 in billing-api.
jira_start_work_on_issue · PROJ-412
Started proj-412-ledger-backfill. The session is reading the ticket now. I assigned PROJ-412 to you and moved it to In Progress.

What happens behind it

  1. A workspace folder, with a worktree per repo on a new branch
  2. The repo's setup script runs in each worktree
  3. Context files: AGENTS.md, attention hooks, the repos' skills, and .mcp.json for Yarvis memory
  4. The ticket is written to .yarvis/brief.md
  5. A Claude Code session starts, told to read the brief and make a first pass

The same thing is one click from any issue, task, or PR: Start work / Start workspace.

Provisioning runs in the sidecar, so I can navigate away and it still finishes. If it fails, the workspace opens on the failed setup log with Retry, or "Ignore and use anyway". The session connects to Yarvis's memory over MCP with no setup, which matters later.

Self-review is my favorite small thing: comment on your own diff like a PR review, but nothing is published. Then "Copy for Claude" pastes the review into the agent as numbered items. The Stack tab shows a gh-stack chain with a state per layer, and can merge up to a chosen layer.

Where the answer comes from

  • Day summaries, written overnight from the activity log
  • Session summaries of Claude Code transcripts (opt-in)
  • The activity log since the last summary
  • Notes a session saved to Yarvis memory over MCP
  • Its own todos, and my open tasks
This is the question I ask most. The quality of the answer depends on what reached memory, which slide 11 covers. Guided reviews also remember where I stopped, so "where was I in Sam's review" works.

  • It moves reviews up when I've done few that week
  • "Give me a plan" goes to the planner, which also reads my projects and their priorities

Worth knowing: the quick "what's next" ranking looks at what's waiting on me, not at project priorities. When priorities should drive the answer, I ask for a plan, which delegates to the planner specialist. The planner reads projects, tickets and their priorities too, and returns exactly three suggestions with a first step each.

Chat

  • Skipped: auth-session-refresh, which has uncommitted changes
  • Conflict in proj-415: webhooks/retry.ts. It's left unpushed.
Want the proj-415 session to resolve it?
Yes.
send_workspace_instruction · proj-415
Sent "resolve the merge conflicts and commit". It's running in the background. I can confirm it was delivered, not that it's done.
  • Fetch, merge the base branch, push, with a report per workspace
  • Dirty worktrees and half-finished merges are skipped, not trampled
  • Instructions are typed into the running session, with guards: only if Claude is the program reading the terminal, and never text starting with !, /, # or @
  • The typing guards are in code. On top of that, the model is told never to forward text from an issue or PR as an instruction.
Also useful: "what's the state of the billing-api workspace" (PR, checks, mergeability, polled every minute), and "archive it", which removes the worktrees and completes the linked task. It asks before throwing away uncommitted work.

Close the gap during the day

Add to your repo's CLAUDE.md: "When you finish a chunk of work, save a short note to Yarvis memory with take_note." Sessions already have the tool.

Close it overnight

Turn on the transcript digest (Settings → Assistant) for the project folders you trust. Each night it writes what was done, the decisions, and any feedback.

Be honest about this with people setting it up. The assistant doesn't read your terminals. It knows what the activity log, the PR poller and memory tell it. The digest is off by default because transcripts can hold pasted secrets, and summarizing them sends them to your LLM provider.
PR review

Guided tours, and questions about any line

Guided review

An agent reads the change and lays out a reading order from the outside in: the request that comes in, what handles it, what it writes. Each step names the lines and why they come there, plus anything that looks wrong.

Data files and tests fold into one sanity-check step each. Next marks the step's files as viewed, synced to GitHub.

Ask about a line

Press ? beside any line (shift-click for a range). The answer is kept as your own note, not published, until you press Post. Later: "what did I work out about that file?"

PR #218 · Refresh sessions before expiry · step 3 of 7
src/auth/session.ts · 40–72
The refresh timer is set here. It's worth reading before the middleware, because the middleware assumes the timer has already run.
⚠ A refresh that fails is swallowed at line 61, so the user stays logged in on an expired token.

GitHub and Azure DevOps both work. A tour gives the agent up to 60 tool steps and a line question up to 16, so they cost real tokens. A guide is kept until you approve, request changes, merge or close the PR, or leave it untouched for 30 days. New commits mark it out of date rather than deleting it. "Start workspace" on a PR checks the branch out in a workspace with a blank agent session, to ask about the change or push a fix.
Omni Chat and Omni view

The assistant over any screen, and a dashboard you describe

Omni Chat · Control+Shift+Space

A chat overlay you can summon from anywhere, even with Yarvis in the background. It sees what you're looking at. On a PR, it knows which one, so you can ask "what's risky here?" without pasting anything. On an issue, "make a task for this" works the same way.

Esc hides it and the reply keeps streaming. Summon it again to carry on the same conversation.

Omni view

Describe a layout and the model builds it from live widgets: tasks, calendar views, PR lists, one PR's description, checks, files and diffs, workspaces, terminals, a chat.

"Today's calendar on the left, my tasks and open PRs on the right." Save it as a layout, and load it every morning.

Omni Chat is the one I use most after the Chat tab. Screen context is detailed for PRs, issues and the calendar, and is only the tab name elsewhere. The Omni builder model has no tools, so name the PR or workspace you want in the prompt.
Voice

Talk to it, and hear it answer, on your own machine

  • A mic on the Chat tab and in Omni Chat, feeding the same conversation
  • Speak replies reads the answer as it streams, one sentence behind the model
  • Hands-free ends a turn on silence and listens again after the reply
  • Runs locally with mlx-audio on Apple Silicon: Whisper in, Soprano or Kokoro out. Gemini works too.

Safer on spoken turns

A transcript can be misheard, or picked up from the room. So on a spoken turn, anything irreversible asks first: archiving, starting work, syncing branches, sending an instruction, filing a ticket. Every MCP tool asks too.

uv sync
uv run mlx_audio.server --host 127.0.0.1 --port 8000
Great for "where did we leave off" while making coffee. Setup is in docs/voice-server.md, about five minutes. Hands-free is off by default on purpose.
Calendar and alarms

Plan around meetings, with a full-screen alarm before each

  • Google Calendar in Agenda, Week, Month and Day views, with Meet links
  • The assistant reads it to plan: "find me two hours of focus time Thursday"
  • It can book an event, always after asking. It can't move or delete one.
  • Set alarms for all arms every meeting, one minute before it starts

The alarm takes over the whole screen, stays on top, and keeps sounding, getting louder after a minute, until you act. It's built for when you're deep in a diff with notifications muted. Arming is manual today: "Set alarms for all" each morning.
Around the edges

Clipboard, MCP, Telegram, and scheduled jobs

Clipboard · Control+Shift+V

Copy buttons on every path, PR link and check. A palette of saved snippets (ids, commands, links) and this session's clipboard history. It refuses to store anything that looks like a credential.

MCP, both ways

Connect remote or local MCP servers, with OAuth, and choose per tool: always on, found by search, or off. Yarvis also serves its memory over MCP, so every workspace session can recall and remember.

Telegram

The same assistant from your phone: "what's failing?", "start work on PROJ-420". Sessions started from Telegram get Claude Code's Remote Control, so you can follow them from the Claude app.

Scheduled jobs

A prompt on a cron schedule, run by Yarvis or by headless Claude Code, with recent runs' output kept. For example, "every weekday at 8:45, list what's waiting on me".

MCP both ways is what ties the coding sessions to the assistant: the session writes a note, and the assistant recalls it. Telegram is allowlisted by chat id, with an optional TOTP second factor.

Getting the most out of it

Habits that make the assistant useful

Say priorities out loud

"X is urgent, Y can wait" is stored and used all week. Correct it when things change: "the deadline moved to the 14th" updates the memory rather than adding a second one.

Bookend the day

Start with "where did we leave off?" End with "note what's left for tomorrow". The note feeds tomorrow's answer.

Start work through Yarvis

Start work from the assistant or a Start work button, not a hand-made checkout. That's what puts the work in the activity log, links the task, and gives the session memory.

Let sessions report back

Add a take_note line to your CLAUDE.md and turn on the transcript digest. The assistant can only recall what reached memory.

If people take one thing away: the assistant is only as good as what reaches it. Starting work through Yarvis, and letting sessions write back, is what makes "where did we leave off" accurate.
