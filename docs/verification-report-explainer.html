How the verification report helps you review a PR

The review workspace's Verification tab is for the person about to read a PR. Claude Code agents read every changed file on your machine and tell you what to read, in what order, and what already looks wrong. It decides nothing and posts nothing on its own.

The /verify-pr skill, which posts a signed report on the PR that CI reads to decide whether the PR can merge automatically, is a different tool. It has its own explainer.

What it's for

Reading a PR cold is slow because the diff shows what changed, not why it matters, what it touches, or where it is likely wrong. The report does a first read for you, so that your own read starts at the parts that matter.

Reader

A person about to review the PR, in a review workspace.

Question

"What should I read, in what order, and what looks wrong?"

The report is a guide to the diff, not a replacement for it. It is judged on whether it gets you to the risky lines faster, and on whether it tells you honestly what it didn't read.

What's in the report

It runs Claude Code on your machine against the PR's checkout. Above Run verification you pick the sections; the summary and must-read files always run. Its progress shows check by check, and every file and line in it opens the diff.

Summary and must-read files

Always run. Each must-read file says why it matters, and lists what already looks off or unclear in it: a branch that looks inverted, a value that seems ignored. These are questions to check while reading, not findings.

Risk

Each change scored on an impact band from 1 to 5 (see below). The band guides your reading rather than deciding a merge. High-band changes appear under Needs attention with what to check, the rest behind Every change.

Checks

Completeness, tests, complexity, performance, comments, observability and code quality. Each is a separate agent with its own brief, so one area doesn't crowd out another.

Simpler approach

Rates the PR as a whole. An agent reads the description and code, then searches the checkout for something the PR could have reused, or a smaller change with the same effect.

Flow diagram

Optional. Traces the whole flow the change sits in, from what starts it (a route, a job, a UI action) to where it ends, with the changed steps highlighted.

Not examined

Changed files that no check read in full, worked out from what the agents actually opened. This list appears at the top of the report, each file with the reason.

Coverage guarantees, and why they matter

A report is only useful if you know what it didn't look at. So:

  • No file is left out to save room. Each changed file's diff is handed to the agents on its own, and each agent is told exactly which patches to read. Only a binary file has no diff. A diff over 2 MB is cut to its first 256 KB, and the agents are told so.
  • Big PRs are split into reading groups of about 512 KB of diff each. Every check runs one agent per group, and their findings are merged. One agent can't hold every diff at once, and what it read first would drop out of its context.
  • Reads are verified, not assumed. A read only counts when it shows the lines. A failed read, a partly read diff, or lines too long to see whole don't count.
  • Bulk is skimmed, not read: the summary agent reads the first 200 lines of each lockfile, minified file, generated or vendored file, and file under dist/ or vendor/, to say what it is. A file the PR adds under dist/ or vendor/ is read in full. Whether a file is marked generated or vendored is read from .gitattributes at the merge-base, so a PR can't mark its own code generated to get it skimmed.

The principles

Read everything, or say what wasn't read

No file is dropped to save room. Yarvis looks at which files the agents actually opened and lists every changed file that no check read in full.

Why: a report that silently skipped a file reads exactly like one that found nothing wrong in it.

One agent per concern

Each check is its own agent with its own brief, reading the same patches as the others.

Why: one agent asked about everything gives each area a little attention. Narrow briefs find more.

Questions, not verdicts

What looks off in a must-read file is a question to check while you read, not a finding. The impact band guides your reading; it doesn't decide a merge.

Why: the report is model-written, and its band isn't checked against test coverage or the import graph, so it is the agent's classification taken as given. You are the one deciding.

Everything from the PR is data

The diffs, descriptions and comments the agents read are treated as untrusted. The flow diagram is drawn in Mermaid's strict mode and shown as an image, where it can't run anything.

Why: the PR's author controls that text, and the agents run on your machine.

The model classifies, code scores

The risk section's agent classifies each change, and impact.ts turns that into a band with a fixed table, the same one /verify-pr uses.

Why: the same classification always gets the same band, so bands mean the same thing from one report to the next.

Nothing leaves without you

The report stays on your machine. A finding reaches the PR or a workspace agent only when you click to send it.

Why: the findings are unchecked model output. You've read the code and can judge whether a finding holds. Nothing else has judged it before you.

The risk section and the impact band

The agent lists each independent change with a kind, a reach and evidence (proven, partial or unproven), and whether it is sensitive (auth and permissions, what an agent may do, secrets, personal data, money, or deleting or migrating data). sidecar/src/verify/impact.ts turns that into a band from 1 (minimal) to 5 (very high).

Evidence is the agent's call on whether tests show the change works: proven (tests cover it), partial (some of it), unproven (none).

Kinds: passive changes no behaviour (comments, formatting, docs, tests only). reorganization moves or splits code with the same behaviour. addition is new code that only runs through other new code in this PR, so nothing that exists today reaches it. removal deletes code something might still reach (if nothing can, it's passive; if something outside the repo can, it's interface). interface changes a signature, exported type, schema, payload or setting key. logic means an input that already exists now gets a different result.

Reach is of the changed thing, not its file: leaf is private to its file, or a test, a script, or a view nothing else uses, local is used in its own feature folder and at most one other, shared is used from two to four other feature folders, core from five or more, or something many features go through (shared libraries, base classes, middleware, the database layer, config).

Then, per change:

  • Unproven adds 1. Partial leaves the band unchanged. Proven takes 1 off a band above 2. It never applies to an interface change, because tests on the changed side don't show that callers elsewhere still work.
  • Sensitive adds 1.
  • Passive changes and proven reorganizations skip these adjustments.
  • A reorganization that isn't proven scores as logic. "Mostly a move" is the mistake this score exists to catch.

Then for the PR: its band is its highest change's band, raised by volume. Many changes in one PR are more likely to include a bad one and harder to revert. Each change adds weight (a folded entry such as "9 comment cleanups" counts nine times): band 1 adds 0, band 2 adds 1, band 3 adds 2, bands 4 and 5 add 4. A total of 8 or more raises the PR one band, and 16 or more raises it two. Volume alone can raise a PR to band 4 but never to 5. When volume raised the band, the report says so: splitting the PR would lower it.

Changes at band 4 or above are listed under Needs attention with what to check. A high change with nothing specific to verify says "No check given: read this change." Every change is behind Every change.

The section's overall level is low (bands 1-2), medium (3) or high (4-5), or the agent's own rating if that is higher. The agent's rating covers what the band can't see, such as a failing CI check, or a reading group whose agent failed and listed nothing.

The table is the same one /verify-pr uses, but the in-app report doesn't check the classification against coverage or the import graph. A change the agent calls proven stays proven. That's why the band here guides your reading rather than deciding anything.

How we build context

For the agents

The surrounding code, not only the diff

The flow diagram and simpler-approach agents follow the code beyond the diff, into the rest of the checkout. A change is often only wrong in how it meets code that didn't change.

The PR's own description

The simpler-approach agent reads what the PR says it is for, then looks for a smaller way to get there, and names the code it would build on.

Every diff, with room to read it

Per-file diffs, an exact list of patches per agent, and reading groups, as in Coverage guarantees.

For you

Where to look, and why

Must-read files with a reason, and under each one what already looks off. Needs attention changes with what to check.

Annotations on the diff itself

A strip above each diff lists the must-read reason, risk concerns and check findings that cite a line. Must-read lines are amber, cited lines red, with the reason on hover. The file tree marks must-read files.

Next to the report: an order to read in

Guided review is a separate tool in the PR bar, run by an agent on your configured LLM provider. It orders the change from the request that arrives to what it finally writes. Data and test files fold into sanity-check steps so the walkthrough stays on logic.

The shape of the flow

The flow diagram shows where the change sits: the changed steps highlighted, traced up to what starts the flow and down to where it ends, so you see how far it reaches before reading a line.

Progress that tracks itself

Marking a file viewed strikes through every must-read, concern and finding in it. Must read counts how many you've done.

A path back to the author

Post to PR posts a finding as a line comment, quoted and with @ mentions escaped, so posting doesn't notify anyone. When the PR came from a Yarvis workspace, Add to workspace puts it in the Yarvis workspace's review comments, labelled as a report finding, so its agent checks it rather than taking it as your instruction. A report for an older head offers neither, since its line numbers may have moved.

Running it

  • From the PR bar: Verification opens the tab. Pick sections and press Run verification. Starting a second run for the same PR joins the one already running.
  • From the assistant: "verify bennettaur/yarvis#612" from chat, voice or Telegram. It uses or creates a review workspace, waits for the clone, and never runs the setup script. It asks first when the PR is large, over budget, of unknown size, or from a repo you haven't registered, since the PR reference may have come from text someone else wrote.
  • Cost: before a large run, or one estimated over the budget in Settings → PR review, you see an estimate and are asked. The budget only warns; a run cut off at a cap would end with nothing to show for what it spent.
  • Staleness: a report for an older head says so and offers Re-run. If a re-run fails or is cancelled, the last good report stays.
