How /verify-pr decides whether a PR can merge

Most PRs should be able to merge without anyone reading them. When a person does need to read one, they should know which part to read first and what to check there. /verify-pr is the Claude Code skill that makes that call and posts it on the PR as a signed report the CI gate reads.

The review workspace's in-app Verification report is a different tool, for the person reading a PR. It has its own explainer.

What we're trying to do

Reading every diff line by line doesn't scale once agents write most of the code. But merging unread code is only safe if something else has done the reading, and if that something can't be talked into a yes. So the system has three jobs:

  1. Measure what can be measured: coverage, whether the new tests fail without the change, whether tests catch small breaking edits, how far each change reaches.
  2. Judge what needs judgment: does the PR do what it says, is it safe, is it simpler than it could be. Agents do this, and their findings are checked before they count.
  3. Route the PR: merge it on its own, have a person glance at screenshots, have the merge reviewer agent read it, or hand it to a person. CI makes the final call from a signed report and its own checks.

The report replaces a first read of the PR, so it has to take less time to read than the diff. A report that lists everything is as slow as reading the code. A report that says "looks fine" is useless. The target is: say plainly what a person must look at, if anything, and give every problem a fix concrete enough that an agent can make it without asking.

The principles

Most design choices below come from one of these. When a rule looks odd, it is usually one of these applied strictly.

Scripts measure, the model judges

scripts/verify/ computes every number in the report: coverage, how well the tests catch the change, how far each change reaches, and the path-based risk floor (see step 3). The model never reports those numbers itself.

Why: a number a model writes is a claim. A number a script writes is one the model can't change.

The model can only make things stricter

The gate recomputes a risk floor from the changed paths. report.ts raises the verdict to what the risk and checks require. Impact claims are checked against coverage and reach.

Why: an agent that misjudges, or reads injected text, can at worst send a PR to a person. It can't lower the tier below the floor the gate computes from the changed paths.

Everything from the PR is data

Title, description, diff, comments, test names, linked issues and the review agents' own reports are all treated as data. The PR text handed to reviewers (title, description, issue text, uncovered lines, test names) is wrapped in tags carrying a random per-run token, so text inside can't fake the closing tag. Agents are told the code and comments they read are untrusted too. An instruction found in any of it becomes a security finding.

Why: the PR's author controls all of that text, and the verifier decides whether their code merges.

Evidence over claims

A test only counts as evidence if it fails on the base branch. A change is only "proven" if coverage backs it. A comment calling something "a refactor" or "safe" is a claim to check, never a reason to score it lower.

Why: a test that passes with or without the change can't tell you whether the change works.

When unsure, go stricter

A sensitive file the skill didn't rate counts as high. A changed file left out of the impact list counts as an unlisted logic change. A judgment the skill can't make gets a human verdict.

Why: a person looking costs a minute. A bad auto-merge costs a revert and trust in the system.

Every finding carries its fix

"Handle the error" isn't a finding. "Catch the ENOENT from readFileSync in load() and return the defaults, with a test that deletes the file" is. Taste isn't a finding at all.

Why: the skill fixes its own findings on your PR before posting. A vague finding can't be fixed without asking, so it stalls the fix-and-recheck loop (step 10).

Signed, pinned and short-lived

A report is signed with your SSH key and names the repo, PR, commit and time. It counts for six hours, on that commit only.

Why: anything holding your GitHub token can post a comment. Only something with access to your signing key can sign one.

Thresholds get checked against reality

Verdict, tier and band are signed into the report data. verify:calibrate compares verdicts, approval paths and risk tiers with later reverts and regressions. The band is signed in so calibration can check it too.

Why: the tier floor, the band table and the volume steps are first guesses. Calibration is how they stop being guesses.

  1. Check the PR can merge

    Conflicts or a branch behind its base: on your own PR it offers to merge the default branch in, otherwise it stops. A failing CI check stops it too. Checks still running are fine, since auto-merge waits for them.

    Why: a report on a PR CI already rejects is wasted work, and the gate would ignore it.

  2. Pin down the goal

    One line saying what the PR is meant to achieve, from its title, description and linked issues. If nobody can say, the goal check is rated concern.

    Why: every other judgment is measured against it. "Does it do what it says, and nothing it doesn't" needs a "what it says".

  3. Collect the facts

    verify:collect writes facts.json:

    • Risk floor: a minimum tier from the changed paths.
    • Diff coverage: which changed lines the tests ran.
    • Baseline: the PR's new or edited tests, run against the base branch's code. Only tests whose own it(...) or test(...) call the diff touches are run this way. One that passes on the base doesn't check the change.
    • Mutation (with --mutation, TypeScript only): Stryker makes small breaking edits to the changed lines and records which ones no test caught.
    • Reach: each changed file's importers, from the import graph.

    Why: coverage alone says a line ran, not that anything checked it. The baseline says whether a test checks the change. Mutation says whether it checks the specific lines.

    For an outside contributor's PR, it uses the base branch's copy of the scripts and --static, which only reads the diff and runs none of the PR's code.

    Why: an untrusted PR's tests would run with your credentials and could post /approve as you.

  4. Run the review agents

    Security, test quality, scope drift, clarity, best practices and dead code always run, in parallel. Performance runs when the PR touches sidecar, Rust or data-loading code. LLM safety runs when it touches prompts, agent tools or the chat, LLM, agents, PR or memory code. Each gets the goal, the base commit, the uncovered lines and the tests that pass without the change, with PR text fenced as untrusted.

    Why: specialists with a narrow brief find more than one general reviewer, and handing them the facts points them at the weak spots instead of making them rediscover them.

  5. Check the findings itself

    Every reviewer finding is a lead. The skill opens the code for each one and keeps only what it can confirm, then sorts them into blocker, major and minor. Before an auto verdict it does its own security pass over the diff. The report lists at most five blockers and majors. A PR with more needs a person anyway, so the report says so and lists the worst.

    Why: reviewers report false positives, and one that read injected text can leave a real problem out or relay an instruction.

  6. Judge each dimension

    Goal, tests, reliability, security, complexity, maintainability, UI and supply chain are each rated pass, concern, fail or n/a, with a note under 140 characters. A concern's note says what would make it pass. Coverage isn't rated by the model; report.ts rates it from the facts.

    Why: short, fixed dimensions keep the report scannable and make it hard to hide a problem in prose.

  7. Assess the risk, check the supply chain, score the impact

    Risk asks whether a safeguard needs a person's eyes. The supply-chain check reads every added or bumped package: is it needed, what kind of bump, who publishes it, any advisories. Impact asks how likely the PR is to break something and how far it would spread. See Risk tier and impact band.

    Why: risk and impact are different questions. A one-line change to tool approval is small but needs a person. A 40-file logic change in the agent loop has no secrets in it but can break everything. The supply-chain check is separate because a bump can pull in new transitive packages the diff of your own code never shows.

  8. Prove UI changes

    When the PR changes what the app renders, the skill uses the demo-flow harness to capture the changed screens, with a before shot from the base branch when the change is easier to see that way, and looks at every image for spinners, error banners and clipped text. If the harness can't reach the change, ui is a concern.

    Why: tests rarely show a layout is right. A screenshot lets a small UI change merge on auto, and lets a big one go to visual (see Verdicts), where you only look at pictures.

  9. Pick a verdict and preview

    The skill writes review.json, previews the rendered report with --dry-run, and reads it as the PR's reader would. On someone else's PR it posts now. On your own PR, if there is anything to fix, it fixes first (step 10) and posts after. Posting signs the data block with your SSH key, replaces the previous report, and refuses if the head moved since collect ran.

    Why: the preview catches a report that's too long or unclear before anyone else sees it. Refusing on a moved head means the report always describes the code that will merge.

  10. Fix, then recheck, then post (your own PR only)

    On a PR you authored, the skill fixes every finding, every flagged check, every new test that passes without the change, and every surviving mutant on a line that matters (a comparison, a branch, a returned value), before posting anything. It runs the checks, pushes, and rechecks. Two rounds at most. It asks first when a fix needs a design decision, weakens a safeguard, touches a high-risk path, CI or .claude/, adds or bumps a dependency, or edits package.json scripts. Findings about injected instructions always go to you. It keeps fixing the rest meanwhile.

    Why: posting first would let the gate merge the unfixed commit. Fixing first means the report you get is for the fixed code. It never comments /approve or merges; that stays your call.

Risk tier and impact band

The report carries two scores. Both set a floor under the verdict, and the stricter one wins.

Risk tier: does a safeguard need checking?

high: reads or moves a secret; launches or types into a shell, process or agent session; changes what an agent may do without asking; touches auth, signing, CI or the verifier; deletes or migrates data; sends data to a new host; a risky package.

standard: a bug would lose data, break a flow the user relies on, or misbehave under load.

low: a bug would be visible and harmless: layout, copy, docs, tests, a refactor the tests pin down.

The skill rates the tier from what the change does, not where it is: a settings screen change that writes a secret is high. CI separately computes a minimum from the paths (below), and the higher of the two wins.

Impact band: how likely to break, how far?

The skill lists each independent change with a kind (passive, reorganization, addition, removal, interface, logic), a reach (leaf, local, shared, core) and evidence (proven, partial, unproven). impact.ts turns that into a band from 1 to 5 with a fixed table.

Why a table: the model classifies, the code scores. The same classification always gets the same band, and the band can be calibrated.

The tier floor

CI doesn't take the report's tier on trust. scripts/verify/tier.ts computes its own floor from the changed paths, their size and risky added lines.

  • Always high, including: the verifier and its workflows, agent instructions and hooks (CLAUDE.md, AGENTS.md, .claude/), secrets, shell access, app permissions, sidecar request handling, tool approval, the MCP server, settings, and what the Chrome extension may do. Also install hooks, verify: scripts, and any .github/ change whose added lines name a secret, a write permission or a privileged trigger.
  • Left for the skill to rate: other workflows, git hooks, build and test config, the schema, and migrations that do more than add. A file the skill doesn't rate counts as high.
  • Standard: registry-only dependency changes, additive migrations, and more than 300 changed lines of code.

The report can raise the floor, never lower it.

The band table

Kinds: passive changes no behaviour (comments, formatting, docs, tests only). reorganization moves or splits code with the same behaviour. addition is new code no existing input reaches without something this PR adds. removal deletes code. interface changes a signature, exported type, schema, payload or setting key. logic means an input that already exists now gets a different result.

Reach is of the changed thing, not its file: leaf is private to its file, local is used in its own feature folder and at most one other, shared from two to four others, core from five or more, or something many features go through (the agent loop, the database client, config).

Then, per change:

  • Unproven adds 1. Proven takes 1 off, but never below 2 and never for an interface, since tests on one side don't show callers elsewhere still work.
  • Sensitive (secrets, auth, agent permissions, data deletion) adds 1.
  • Passive changes and proven reorganizations never move.
  • A reorganization that isn't proven scores as logic. "Mostly a move" is the mistake this score exists to catch.

Then for the PR: its band is its highest change's band, raised by volume. Many changes in one PR are more likely to include a bad one and harder to revert. Each change adds weight by its band (0 for band 1, 1, 2, then 4 for bands 4 and 5). A total of 8 raises the PR one band, 16 raises it two. Volume alone can take a PR to 4 but not 5, so a pile of small changes reaches the merge reviewer but not a person. When volume raised the band, the report says so, and when the changes are independent the skill adds a minor finding on how to split the PR.

Facts sit under the classification

report.ts checks the model's classification against the facts and never scores below them:

  • A proven claim counts as partial unless tests ran every changed line in its files.
  • A change that could alter behaviour counts at no less than the reach the import graph measured.
  • A changed source file no entry names counts as an unlisted, partly tested logic change.

Changes at band 4 or above are listed under Needs attention, each with a one-sentence check naming what a reviewer should confirm: "runAgentTurn still saves nothing after an abort", not "check the logic".

Verdicts and merge paths

Verdicts go from loosest to strictest. The verdict can't be looser than the risk tier or the impact band allows, and the gate checks again.

VerdictWhenWhat happens
auto Low or standard risk, no blocker or major finding, no flagged check, enough of the changed lines covered. Minor findings and small UI changes the screenshots show working are fine. The gate approves as soon as the signed report lands. Auto-merge waits for the rest of CI.
visual The same, but the UI change is one a person should see: a new screen or flow, a layout or design change. You look at the screenshots in the report and comment /approve.
agent A major finding, any dimension rated concern, an unchecked dependency change, UI with no screenshots, tests that miss many mutants, or impact band 4. Ask Yarvis to have the merge reviewer check it. Its signed approve lets the gate approve. The gate still refuses blockers and high risk, as a backstop.
human High risk, impact band 5, a blocker, a failed check, tests that fail on the PR, or a judgment the skill can't make. You read it and comment /approve. The risk reasons name the safeguards to check.

The gate only approves on a report or an agent review when VERIFY_MODE is enforce, the PR's author is a trusted user, and the PR isn't a draft. In the default shadow mode it only sets the Verification report commit status and never approves. /approve works in both.

The visual and agent paths exist so that "not safe to merge alone" doesn't always mean "a person reads the whole diff". Most PRs that aren't auto need one specific thing checked, and the report says what.

Why reports are signed

Claude Code, Yarvis and anything else with your GitHub token post as you. That includes a stolen token or a PR's test running under your gh login. If the gate trusted any report comment from your account, any of those could post an auto report and get a PR merged.

Your SSH signing key

Your git SSH signing key, usually held in 1Password. Used by /verify-pr. Signs as verify-pr in namespace yarvis-verify. Can sign any verdict.

The merge reviewer's key

Lives in Yarvis's Settings → Credentials. Signs as yarvis-merge-reviewer in namespace yarvis-agent-review. Can only sign a yes or no on an agent report you already signed, at the same commit.

The reviewer has its own key because nobody is there to unlock 1Password when it runs, and because it shouldn't be able to do what your key does. Each signature names the repo, PR, commit and time, so it can't be moved to another PR, a newer push, or reused after six hours. The gate always runs main's copy of itself, and its own files are always high risk.

A signature shows the report was signed on your machine. It doesn't show the run was honest: while 1Password is unlocked, an agent tricked by injected text could get the key to sign a report it wrote itself. That is why the gate keeps its own tier floor and refuses high risk and blockers whatever the report says. The full threat table is in docs/verification.md.

How we build context

A diff shows what changed, not why it matters or what it touches. The skill hands its review agents, and the person who may read the PR after them, the context they would otherwise have to rebuild.

For the review agents

A goal to measure against

Pinned before any review starts (step 2) and passed to every agent. Scope drift and the goal check depend on it.

Facts instead of guesses

Reviewers get the uncovered lines and the tests that pass without the change, so they start at the weak spots. The impact step gets each file's importers from the import graph, so reach isn't guessed.

The repo's own rules

Reliability and security are judged against the invariants in AGENTS.md for the areas the PR touches: untrusted text, worktree paths, tool approval. The bar is the codebase's, not a generic checklist.

A clear line between data and instructions

PR text goes in tagged blocks the agent is told are untrusted. That makes it much harder for hostile text to pass as instructions. It doesn't make it impossible, which is why the gate's own checks don't depend on it.

For the person reading the report

Where to look, and why

Needs attention lists every change at band 4 or above with a one-sentence check. High-risk reasons name the safeguard: "types into the agent's PTY: check prepare_instruction still runs first", not "touches pty.rs".

A fix with every problem

Each finding names the file, the change to make and how to check it, so whoever picks it up, a person or the fix loop, needs nothing else.

Pictures for UI changes

Screenshots from the demo harness, with a before shot when it helps, so a visual verdict needs a glance rather than a checkout.

A short, fixed shape

The same dimensions in the same order, each with a note under 140 characters, and minor findings folded away. The report has to be quicker to read than the diff.

Rechecking after fixes

/verify-pr <N> --recheck re-verifies what the last report flagged, plus the commits pushed since, instead of the whole PR. It still posts a complete report for the new head, since the gate reads only the latest one.

  • Facts are always re-collected. Coverage, baseline and mutation are measured, not judged, so a recheck re-runs them rather than carrying them forward.
  • Review covers the fix diff. The security reviewer always runs on it, plus the agents for each dimension the last report flagged.
  • Each old finding is settled against the code: dropped if fixed, kept if not, rewritten if partly fixed.
  • A recheck never lowers the tier or the impact band. The previous reasons may not name every risky change, so lowering either needs a full pass.
  • It falls back to a full run when the last run's review.json and facts.json don't match the posted report, the old head isn't in the clone, the fix diff is more than a third of the PR, or the PR now touches a file the old facts didn't list.

Why: the fix loop would be slow and expensive if every round re-reviewed everything. The verdict can loosen as findings get fixed; that is the point of the fix loop. But a recheck that could lower the tier or the band would be a way to get a risky PR through on a lighter check, so it can only keep or raise those.

After merge: reverts and calibration

Auto-revert

verify-revert.yml runs when CI fails on main. If the gate auto-approved the PR behind that commit (or approved it on the merge reviewer's word), CI passed on the commit before it, and no revert exists yet, it re-runs the failed jobs once. If they fail again, it opens a revert PR and comments on the original. PRs a person approved are left alone.

Calibration

bun run verify:calibrate --days 60 lists each verdict and approval path against how many merges were later reverted or caused a regression. Add Regression-from: #N to a fix PR's description so a fix-forward counts too.

The thresholds in the tier floor, the band table and the volume steps are first guesses. Calibration shows which verdicts are too loose or too strict.
