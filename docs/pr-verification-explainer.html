Yarvis · PR verification

How Yarvis verifies pull requests

Most PRs should be able to merge without anyone reading them. When a person does need to read one, they should know which part to read first and what to check there. Everything below serves one of those two goals.

What we're trying to do

Reading every diff line by line doesn't scale once agents write most of the code. But merging unread code is only safe if something else has done the reading, and if that something can't be talked into a yes. So the system has three jobs:

  1. Measure what can be measured: coverage, whether the new tests fail without the change, whether tests catch small breaking edits, how far each change reaches.
  2. Judge what needs judgment: does the PR do what it says, is it safe, is it simpler than it could be. Agents do this, and their findings are checked before they count.
  3. Route the PR: merge it on its own, have a person glance at screenshots, have the merge reviewer agent read it, or hand it to a person. CI makes the final call from a signed report and its own checks.

The report replaces a first read of the PR, so it has to take less time to read than the diff. A report that lists everything is as slow as reading the code. A report that says "looks fine" is useless. The target is: say plainly what a person must look at, if anything, and give every problem a fix concrete enough that an agent can make it without asking.

Two tools, two readers

There are two verification tools. They share ideas and some code, but they answer different questions for different readers.

The /verify-pr skill

A Claude Code skill run in a workspace session. It measures the PR, runs review agents, judges it and posts a signed report on the PR. The CI gate reads that report to decide whether the yarvis bot can approve and auto-merge.

Reader
CI, and the maintainer deciding whether to merge.

Question
"Can this merge, and who, if anyone, has to look first?"

The in-app Verification report

The Verification tab in a review workspace. Claude Code agents read every changed file's diff on your machine and write a report that stays local: a summary, must-read files, risk, checks, a simpler-approach rating and an optional flow diagram.

Reader
A person about to review the PR.

Question
"What should I read, in what order, and what looks wrong?"

Two supporting pieces sit around them:

  • The merge reviewer (merge-reviewer specialist): when a /verify-pr report's verdict is agent, it reads the PR, the report and the code the report points at, then posts a signed approve or reject.
  • The guided review: an agent orders the change into a tour, outside in, with what it thinks is wrong at each step. It's how a person reads a PR once the report says they should.

Both tools use the same impact scorer (sidecar/src/verify/impact.ts), so a change scores the same band in the review workspace as it does on the PR.

The principles

Most design choices below come from one of these. When a rule looks odd, it is usually one of these applied strictly.

Scripts measure, the model judges

scripts/verify/ computes coverage, the baseline run, mutation scores, import-graph reach and the path tier. The model never reports those numbers itself.

Why: a number a model writes is a claim. A number a script writes is a fact the model has to work around.

The model can only make things stricter

The gate recomputes a risk floor from the changed paths. report.ts raises the verdict to what the risk and checks require. Impact claims are checked against coverage and reach.

Why: an agent that misjudges, or reads injected text, can at worst send a PR to a person. It can't send a risky PR to auto-merge.

Everything from the PR is data

Title, description, diff, comments, test names, linked issues and the review agents' own reports are fenced in per-run nonce tags. An instruction found inside them becomes a security finding.

Why: the PR's author controls all of that text, and the verifier decides whether their code merges.

Evidence over claims

A test only counts as evidence if it fails on the base branch. A change is only "proven" if coverage backs it. A comment calling something "a refactor" or "safe" is a claim to check, never a reason to score it lower.

Why: a test that passes without the change would still pass if the change were reverted, so it doesn't check the change.

When unsure, go stricter

A sensitive file the skill didn't rate counts as high. A changed file left out of the impact list counts as an unlisted logic change. A failed decision means a person looks.

Why: a person looking costs a minute. A bad auto-merge costs a revert and trust in the system.

Every finding carries its fix

"Handle the error" isn't a finding. "Catch the ENOENT from readFileSync in load() and return the defaults, with a test that deletes the file" is. Taste isn't a finding at all.

Why: the skill fixes its own findings on your PR before posting. A vague finding can't be fixed without asking, so it blocks the loop.

Signed, pinned and short-lived

A report is signed with your SSH key and names the repo, PR, commit and time. It counts for six hours, on that commit only.

Why: anything holding your GitHub token can post a comment. Only your machine can sign one.

Thresholds get checked against reality

Verdict, tier and band are signed into the report data. verify:calibrate compares them with later reverts and regressions.

Why: the band table and volume steps are first guesses. Calibration is how they stop being guesses.

  1. Check the PR can merge

    Conflicts or a branch behind its base: on your own PR it offers to merge the default branch in, otherwise it stops. A failing CI check stops it too. Checks still running are fine, since auto-merge waits for them.

    Why: a report on a PR CI already rejects is wasted work, and the gate would ignore it.

  2. Pin down the goal

    One line saying what the PR is meant to achieve, from its title, description and linked issues. If nobody can say, the goal check is rated concern.

    Why: every other judgment is measured against it. "Does it do what it says, and nothing it doesn't" needs a "what it says".

  3. Collect the facts

    verify:collect writes facts.json: the path-based risk floor, diff coverage, and the baseline run, which runs the PR's new or edited tests against the base branch's code. A test only counts when the diff touches its own it(...) or test(...) call. With --mutation, Stryker makes small breaking edits to the changed lines and records which ones no test caught. It also records each changed file's importers from the import graph.

    For an outside contributor's PR, it uses the base branch's copy of the scripts and --static, which only reads the diff and runs none of the PR's code.

    Why: coverage alone says a line ran, not that anything checked it. The baseline says whether a test checks the change. Mutation says whether it checks the specific lines. An untrusted PR's tests would run with your credentials and could post /approve as you.

  4. Run the review agents

    Security, test quality, scope drift, clarity, best practices and dead code always run, in parallel. Performance runs when the PR touches sidecar, Rust or data-loading code. LLM safety runs when it touches prompts, agent tools or the chat, LLM, agents, PR or memory code. Each gets the goal, the base commit, the uncovered lines and the tests that pass without the change, with PR text fenced as untrusted.

    Why: specialists with a narrow brief find more than one general reviewer, and handing them the facts points them at the weak spots instead of making them rediscover them.

  5. Check the findings itself

    Every reviewer finding is a lead. The skill opens the code for each one and keeps only what it can confirm, then sorts them into blocker, major and minor. Before an auto verdict it does its own security pass over the diff. At most five blockers and majors are kept; more than that means a person is needed anyway.

    Why: reviewers report false positives, and one that read injected text can leave a real problem out or relay an instruction.

  6. Judge each dimension

    Goal, tests, reliability, security, complexity, maintainability, UI and supply chain are each rated pass, concern, fail or n/a, with a note under 140 characters. A concern's note says what would make it pass. Coverage isn't rated by the model; report.ts rates it from the facts.

    Why: short, fixed dimensions keep the report scannable and make it hard to hide a problem in prose.

  7. Assess the risk, check the supply chain, score the impact

    Risk asks whether a safeguard needs a person's eyes. The supply-chain check reads every added or bumped package: is it needed, what kind of bump, who publishes it, any advisories. Impact asks how likely the PR is to break something and how far it would spread. See Risk tier and impact band.

    Why: these are different questions. A one-line change to tool approval is small but needs a person. A 40-file logic change in the agent loop has no secrets in it but can break everything.

  8. Prove UI changes

    When the PR changes what the app renders, the skill uses the demo-flow harness to capture the changed screens, sometimes with a before shot, and looks at every image for spinners, error banners and clipped text. If the harness can't reach the change, ui is a concern.

    Why: tests rarely show a layout is right. A screenshot lets a small UI change merge on auto, and lets a big one go to visual where you only look at pictures.

  9. Pick a verdict, preview and post

    The skill writes review.json, previews the rendered report with --dry-run, and reads it as the PR's reader would. Posting signs the data block with your SSH key, replaces the previous report, and refuses if the head moved since collect ran.

    Why: the preview catches a report that's too long or unclear before anyone else sees it. Refusing on a moved head means the report always describes the code that will merge.

  10. Fix, then recheck, then post (your own PR only)

    On a PR you authored, the skill fixes every finding, flagged check, test in baseline.notDetecting and surviving mutant on a line that matters, before posting anything. It runs the checks, pushes, and rechecks. Two rounds at most. It asks first when a fix needs a design decision, weakens a safeguard, touches CI or .claude/, or changes a dependency.

    Why: posting first would let the gate merge the unfixed commit. Fixing first means the report you get is for the fixed code. It never comments /approve or merges; that stays your call.

Risk tier and impact band

The report carries two scores. Both set a floor under the verdict, and the stricter one wins.

Risk tier: does a safeguard need checking?

high: reads or moves a secret; launches or types into a shell, process or agent session; changes what an agent may do without asking; touches auth, signing, CI or the verifier; deletes or migrates data; sends data to a new host; a risky package.

standard: a bug would lose data, break a flow the user relies on, or misbehave under load.

low: a bug would be visible and harmless: layout, copy, docs, tests, a refactor the tests pin down.

Rated from what the change does, not where it is. A settings screen change that writes a secret is high.

Impact band: how likely to break, how far?

The skill lists each independent change with a kind (passive, reorganization, addition, removal, interface, logic), a reach (leaf, local, shared, core) and evidence (proven, partial, unproven). impact.ts turns that into a band from 1 to 5 with a fixed table.

Why a table: the model classifies, the code scores. The same classification always gets the same band, and the band can be calibrated.

The tier floor

CI doesn't take the report's tier on trust. scripts/verify/tier.ts computes its own floor from the changed paths, their size and risky added lines. The verifier and its workflows, agent instructions and hooks, secrets, shell access, tool approval and the MCP server are always high. Workflows, git hooks, build config, the schema and non-additive migrations are sent to the skill to assess, and a file it doesn't rate counts as high. The report can raise the floor, never lower it.

Then, per change:

  • Unproven adds 1. Proven takes 1 off, but never below 2 and never for an interface, since tests on one side don't show callers elsewhere still work.
  • Sensitive (secrets, auth, agent permissions, data deletion) adds 1.
  • A reorganization that isn't proven scores as logic. "Mostly a move" is the mistake this score exists to catch.

Then for the PR: its band is its highest change's band, raised by volume. Many changes in one PR are more likely to include a bad one and harder to revert. Volume alone can take a PR to 4 but not 5, so a pile of small changes reaches the merge reviewer but not a person. When volume raised the band, the report says so and suggests how to split the PR.

Facts sit under the classification

report.ts checks the model's classification against the facts and never scores below them:

  • A proven claim counts as partial unless tests ran every changed line in its files.
  • A change that could alter behaviour counts at no less than the reach the import graph measured.
  • A changed source file no entry names counts as an unlisted, partly tested logic change.

Changes at band 4 or above are listed under Needs attention, each with a one-sentence check naming what a reviewer should confirm: "runAgentTurn still saves nothing after an abort", not "check the logic".

Verdicts and merge paths

Verdicts go from loosest to strictest. The verdict can't be looser than the risk tier or the impact band allows, and the gate checks again.

VerdictWhenWhat happens
auto Low or standard risk, no blocker or major finding, no flagged check, enough of the changed lines covered. Minor findings and small UI changes the screenshots show working are fine. The gate approves as soon as the signed report lands. Auto-merge waits for the rest of CI.
visual The same, but the UI change is one a person should see: a new screen or flow, a layout or design change. You look at the screenshots in the report and comment /approve.
agent A major finding, a concern, an unchecked dependency change, UI with no screenshots, tests that miss many mutants, or impact band 4. Ask Yarvis to have the merge reviewer check it. Its signed approve lets the gate approve, unless there is a blocker or the PR is high risk.
human High risk, impact band 5, a blocker, a failed check, or a judgment the skill can't make. You read it and comment /approve. The risk reasons name the safeguards to check.

The visual and agent paths exist so that "not safe to merge alone" doesn't always mean "a person reads the whole diff". Most PRs that aren't auto need one specific thing checked, and the report says what.

Why reports are signed

Claude Code, Yarvis and anything else with your GitHub token post as you. That includes a stolen token or a PR's test running under your gh login. If the gate trusted any report comment from your account, any of those could post an auto report and get a PR merged.

Your SSH signing key

Lives in 1Password. Used by /verify-pr. Signs as verify-pr in namespace yarvis-verify. Can sign any verdict.

The merge reviewer's key

Lives in Yarvis's Settings → Credentials. Signs as yarvis-merge-reviewer in namespace yarvis-agent-review. Can only sign a yes or no on an agent report you already signed, at the same commit.

The reviewer has its own key because nobody is there to unlock 1Password when it runs, and because it shouldn't be able to do what your key does. Each signature names the repo, PR, commit and time, so it can't be moved to another PR, a newer push, or reused after six hours. The gate always runs main's copy of itself, and its own files are always high risk.

A signature shows the report was signed on your machine. It doesn't show the run was honest: a prompt-injected agent in a session 1Password unlocked could sign other text. That is why the gate keeps its own tier floor and refuses high risk and blockers whatever the report says. The full threat table is in docs/verification.md.

The in-app verification report

The review workspace's Verification tab is for the person reviewing. It runs Claude Code on your machine against the PR's checkout, never posts anything on its own, and turns into a to-do list as you read.

What it contains

Summary and must-read files

Always run. Each must-read file says why it matters, and lists what already looks off or unclear in it: a branch that looks inverted, a value that seems ignored. These are questions to check while reading, not findings.

Risk

The same impact scoring as /verify-pr. High-band changes appear under Needs attention with what to check, the rest behind Every change.

Checks

Completeness, tests, complexity, performance, comments, observability and code quality. Each is a separate agent with its own brief, so one area doesn't crowd out another.

Simpler approach

Rates the PR as a whole. An agent reads the description and code, then searches the checkout for something the PR could have reused, or a smaller change with the same effect.

Flow diagram

Optional. Traces the whole flow the change sits in, from what starts it (a route, a job, a UI action) to where it ends, with the changed steps highlighted.

Not examined

Yarvis counts, from the files the agents actually opened, which changed files no check read in full. They are listed first, with why.

Coverage guarantees, and why they matter

A report is only useful if you know what it didn't look at. So:

  • No file is left out to save room. Each changed file's diff is handed to the agents on its own, and each check gets its exact file list.
  • Big PRs are split into reading groups of about 512 KB, one agent per group per check, findings merged. One agent can't hold every diff, and what it read early would drop out of its context.
  • Reads are verified, not assumed. A read only counts when it shows the lines. A failed read, a partly read diff, or lines too long to see whole don't count.
  • Bulk is skimmed, not read: lockfiles, minified files, and generated or vendored files. Those marks are read at the merge-base, so a PR can't mark its own code generated to get it skimmed.

How we build context

Both the agents and the human reader start with the same problem: a diff shows what changed, not why it matters or what it touches. A lot of the system exists to hand each reader the context they'd otherwise have to rebuild.

For the agents

A goal to measure against

Pinned before any review starts, and passed to every agent. Scope drift, completeness and the goal check all depend on it.

Facts instead of guesses

Reviewers get the uncovered lines and the tests that pass without the change, so they start at the weak spots. The impact step gets each file's importers from the import graph, so reach isn't guessed.

The repo's own rules

Reliability and security are judged against the invariants in AGENTS.md for the areas the PR touches: untrusted text, worktree paths, tool approval. The bar is the codebase's, not a generic checklist.

Room to read everything

Per-file diffs, exact file lists per check, and reading groups sized so no agent has to drop early diffs from its context.

The surrounding code, not only the diff

The flow diagram and simpler-approach agents search the whole checkout. A change is often only wrong in how it meets code that didn't change.

A clear line between data and instructions

PR text goes in nonce-tagged blocks the agent is told are untrusted. That lets agents read hostile text closely without acting on it.

For the person reading

Where to look, and why

Must-read files with a reason. Needs attention changes with a one-sentence check. High-risk reasons that name the safeguard: "types into the agent's PTY: check prepare_instruction still runs first", not "touches pty.rs".

Annotations on the diff itself

In a review workspace, a strip above each diff lists the must-read reason, risk concerns and check findings that cite a line. Must-read lines are amber, cited lines red, with the reason on hover.

An order to read in

The guided review walks the change outside in, from the request that arrives to what it finally writes. Data and test files fold into sanity-check steps so the walkthrough stays on logic.

The shape of the flow

The flow diagram shows where the change sits: changed code highlighted, the callers and tables around it drawn in, so you see the blast radius before reading a line.

Progress that tracks itself

Marking a file viewed strikes through every must-read, concern and finding in it. Must read counts how many you've done.

A path back to the author

A finding you've read can be posted to the PR as a line comment, or added to the Yarvis workspace's review comments, where its agent treats it as a problem to check rather than your request.

Rechecking after fixes

/verify-pr <N> --recheck re-verifies what the last report flagged, plus the commits pushed since, instead of the whole PR. It still posts a complete report for the new head, since the gate reads only the latest one.

  • Facts are always re-collected. Coverage, baseline and mutation are measured, not judged, so they're cheap to trust and cheap to redo.
  • Review covers the fix diff. The security reviewer always runs on it, plus the agents for each dimension the last report flagged.
  • Each old finding is settled against the code: dropped if fixed, kept if not, rewritten if partly fixed.
  • A recheck never lowers the tier or the impact band. The previous reasons may not name every risky change, so lowering either needs a full pass.
  • It falls back to a full run when the local files don't match the posted report, the old head isn't in the clone, the fix diff is more than a third of the PR, or the PR now touches a file the old facts didn't list.

Why: the fix loop would be slow and expensive if every round re-reviewed everything. But a recheck that could loosen the verdict would be a way to launder a risky PR, so it can only keep or tighten.

After merge: reverts and calibration

Auto-revert

When CI fails on main and the gate auto-approved the PR behind that commit (or the merge reviewer did), verify-revert.yml re-runs the failed jobs once. If they fail again, it opens a revert PR and comments on the original. PRs a person approved are left alone.

Calibration

bun run verify:calibrate --days 60 lists each verdict and approval path against how many merges were later reverted or caused a regression. Add Regression-from: #N to a fix PR's description so a fix-forward counts too.

This closes the loop. The thresholds in the tier floor, the band table and the volume steps are first guesses. Calibration shows which verdicts are too loose or too strict.
